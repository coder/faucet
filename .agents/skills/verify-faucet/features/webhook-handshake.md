# Webhook handshake

An agent that subscribes a callback URL with `events/subscribe` can ask the operator's faucet to check, before it stores anything, that the endpoint behind the URL agrees to receive events. This is the verification handshake of the MCP Events extension (SEP-3415, endpoint verification option 1). The operator turns it on with `FAUCET_WEBHOOK_CALLBACK_VERIFICATION=handshake`. Faucet then sends one signed `POST` to the URL, through a guarded client, and stores the subscription only when the endpoint answers the nonce. The main faucet uses the origin allowlist instead and sends nothing (see [events/subscribe](events-subscribe.md)). At PR 7a faucet sends no event yet. This is the guarded sender that delivery will use.

## Sub-features

- The mode is `FAUCET_WEBHOOK_CALLBACK_VERIFICATION=handshake`. It needs `FAUCET_WEBHOOK_KEY`, and `FAUCET_WEBHOOK_ALLOWED_ORIGINS` must be unset. The startup refusals are in [startup](startup.md). The default, and the value `allowlist`, keep the origin check.
- The request is a `POST` to the callback URL with `Content-Type: application/json`, a `User-Agent`, and `X-MCP-Subscription-Id` set to the `id` that the subscribe reply will carry. The body is `{"type":"verification","challenge":"<nonce>"}` and nothing else. The nonce is 32 random bytes in unpadded base64url (43 characters), new for every request, never stored and never logged.
- The request is signed like a delivery, with the Standard Webhooks headers `webhook-id` (`msg_verification_` and 22 random URL-safe characters), `webhook-timestamp` (Unix seconds) and `webhook-signature` (`v1,` and the base64 of the HMAC-SHA256 of `<id>.<timestamp>.<body>`), keyed with the base64 decoding of the subscriber's own `whsec_` secret. It carries no `Authorization` header, no cookie and no credential of faucet. An endpoint that does not hold the secret cannot check the signature, and so should not answer.
- The endpoint passes when it answers `2xx` with a JSON object whose only member is `challenge`, with the nonce as a string. Spaces, newlines and a trailing newline are fine. A wrong nonce, an empty body, a request body reflected back (it has a `type` member too), an extra member, a repeated member, a non-string value, text after the object, an array, or more than 1 KiB of answer are `challenge_failed`. The comparison is constant-time.
- A `4xx` answer is `http_4xx` and a `5xx` answer is `http_5xx`, even with a correct body. Any other status outside `2xx`, a redirect included, is `challenge_failed`. A refused connection, a name that does not resolve and a host that points to a non-public address are `connection_refused`, all alike, so a caller cannot tell which names are inside the network. A certificate for another name, an untrusted one, or a server that does not speak TLS is `tls_error`. No answer in 5 seconds is `timeout`.
- A refusal is the error -32027 with `data` `{"reason": "<category>"}` and a fixed message. It never quotes the URL, the secret, the nonce or anything that the endpoint sent. It writes no row. The server logs `callback not verified` with `login` and `reason` only. A failure is not remembered, so the next call tries again.
- A success is remembered per (login, URL) for 10 minutes. A refresh, and another event or `pr` on the same URL, send nothing. Another login on the same URL is verified again.
- The client is `faucet.NewHTTPClient`. It refuses `http`, any address that is not public (loopback, private, link-local, CGNAT, multicast, unspecified, NAT64, 6to4, Teredo and the other special ranges, and an IPv4-mapped address whose IPv4 address is one of those), and user info in the URL. It resolves the name, refuses the whole answer if one address is not public, and dials the address it checked. It verifies the certificate against the host name. It follows no redirect, ignores the proxy variables, stops at 5 seconds and refuses a response body past 64 KiB.
- Each login has a bucket per destination of 5 handshakes that refills one every 12 seconds, and each destination has a bucket for all logins of 60 that refills one a second, so one login that keeps failing cannot starve another, and many logins cannot flood a host. A host name counts in lower case without a trailing dot or a port, and an IP address counts by its canonical form, so `127.0.0.1`, `[::ffff:127.0.0.1]` and `[0:0:0:0:0:ffff:7f00:1]` share one bucket. A handshake that fails keeps its tokens spent, and one that the endpoint answers correctly gives both back. When a bucket is empty the call is the error -32025 with `data` `{"limit": "callbackVerifications"}`, and nothing is sent or written.
- A binary built with `-tags faucet_e2e` also lets the client reach `http://127.0.0.1:<port>`. The tagged binary logs a warning at start. The production binary has no variable for it, so it answers -32602 to an `http` or loopback callback URL.

## How to get to it (user POV)

An agent that runs a webhook receiver sends `events/subscribe` to `/mcp` with `Authorization: Bearer <GitHub token>` and `Mcp-Name: <event name>`. It generates the `whsec_` secret itself, and it must verify the signature of the first request before it answers. The reply is the usual subscribe result, or one of the errors above. The agent cannot see any of the nonce, the signature, the log or the other hosts' buckets.

## Driving it with e2e

`tests/handshake.e2e.ts`. `app.mjs` also builds `faucet-e2e` with `-tags faucet_e2e` and starts a callback receiver on `127.0.0.1`. A test starts a handshake faucet with `faucet.withFaucet({ FAUCET_WEBHOOK_KEY, FAUCET_WEBHOOK_CALLBACK_VERIFICATION: 'handshake' }, fn, { e2eBuild: true })`, registers a secret for an id with `receiver.register(id, secret)`, and subscribes to `receiver.callback(behavior, id)`. The behaviors are in `app.mjs`: `echo` (checks the signature with the registered secret, then answers the nonce, else 401), `wrong`, `reflect`, `error500`, `notfound`, `redirect` (302 to `/hook/internal/<id>`), `slow` (never answers) and `large` (the answer, then 4 KiB of spaces). `receiver.requests(id)` returns what the receiver got: the headers, the body and `signature`, its own verdict (`valid`, `invalid`, `missing` or `unregistered`), which it computes with Node crypto and no code of faucet. The startup refusals of the new variable are in `tests/startup.e2e.ts`. Not reachable from a browser: use `run_tests {files: ["tests/handshake.e2e.ts"]}`.

## Proof

The receiver's `signature` is `valid` for the handshake request, so the HMAC was made over the exact bytes with the subscriber's secret. The headers, the body keys and the nonce shape are checked, and `faucet.leaksSecret` is false for the recorded request. The reply of a refusal has the category and a fixed message. `faucet.subscriptions(id)` is empty after every refusal, and the log of the started faucet holds the line `callback not verified` with the reason, and holds neither the secret, nor its base64 part, nor the id that is in the URL path, nor any nonce that the receiver saw. The redirect target is never requested. The sixth failing handshake to `127.0.0.1`, after five that wrote it in five spellings (`[::ffff:127.0.0.1]` and the like), is -32025 and the receiver has no request for it. The production binary answers -32602 and the receiver sees nothing.

## Charters

No charter. Every check needs the control calls of the receiver, a second build of the faucet or its log, and a browser session reaches none of them.

## Gotchas

- Every callback of these tests is on `127.0.0.1`, which is one host for the rate limit, and the tests of one faucet all use the login `verify-user`. A test that fails more than 5 handshakes needs its own faucet. The tests keep to 4 or 5 failures a faucet.
- The `slow` case takes the full 5 seconds, so the test that holds it takes about 6.
- Only the faucet that `withFaucet` starts with `e2eBuild: true` can reach the receiver. The main faucet and the cron faucet use the production binary.
- The receiver checks the signature as `valid` only under the secret that the test registered for the id. A test that registers another secret plays an endpoint that cannot verify the request, which answers 401.
- `webhook-timestamp` is the server's clock. The test allows a minute.
