# Security model

## Three kinds of caller

Faucet returns events only for repositories that the caller may read. A caller of `/github/mcp` is one of three kinds:

| Caller | Its bearer token | Who decides what it may read | GitHub token that faucet keeps for it |
| --- | --- | --- | --- |
| A [browser login](browser-login.md) | A faucet access token | GitHub, asked with the user's GitHub App token | The user's access token and refresh token, sealed |
| A [service](service-accounts.md) | A faucet access token | The operator's grants. Faucet asks GitHub nothing. | None |
| A [workload](service-accounts.md#log-in-with-a-workload-identity) | A faucet access token, for a token that its platform signed | The operator's grants, as for a service, since it logs in as one | None |

For a service and a workload, faucet holds no GitHub token of the caller. For a browser login, faucet keeps the user's GitHub App token, sealed with AES-256-GCM under `FAUCET_TOKEN_KEY`, and gives the client its own short-lived token. The client never sees the GitHub token. Whoever holds both faucet's database and `FAUCET_TOKEN_KEY` can open those tokens and act as each of those users within the App's permissions, and with the App's client secret can also refresh them. That is why the App gets read-only permissions.

## Access to events

Every `/github/mcp` request carries its bearer token as `Authorization: Bearer <token>`. A bearer that starts with `fct_`, `fcr_` or `fcs_` is a faucet token. Faucet checks it itself and never sends it to GitHub. Faucet mints access tokens for service clients and for the sessions of browser logins, each valid for 15 minutes on the one endpoint it was issued for, and every other faucet token is 401.

Any other bearer, a GitHub token among them, is 401 too, with the same `WWW-Authenticate` challenge as a request with no token, which names the endpoint's metadata so that the client can find the login server. Faucet never sends a bearer to GitHub. It takes no GitHub token because GitHub cannot say what one may read: `GET /repos/{owner}/{name}` answers a fine-grained token that holds only the `Metadata` permission, or a user token of another GitHub App, for a private repository whose pull requests and checks that token cannot read, and no GitHub API reports a fine-grained token's permissions.

Because no request reaches the MCP server without a bearer token, faucet turns off the go-sdk's DNS-rebinding check, which refuses a loopback listener reached under another `Host`. That check protects a local server that trusts whoever can reach it, and it refused every request on Vercel, whose runtime hands each request to faucet on a loopback address under faucet's public `Host`.

A browser login is checked with `GET /repos/{owner}/{name}`, sent with the GitHub token that faucet keeps for the user, a user token of faucet's own GitHub App. GitHub answers it for a repository where the App is installed and that the user can read, so the answer is about the user and not about a token that someone narrowed. A repository the user can't read gives the same `Forbidden` error as one that doesn't exist. Faucet refreshes that token first when it is about to expire. When GitHub rejects it, faucet refreshes it once and asks again. Faucet stores each check that passes, per GitHub user and repository, and a session takes a stored check without asking GitHub only when faucet made it after that session's last refresh. At each refresh faucet asks GitHub again about the 50 repositories that the user used last, among those used in the last 15 minutes, and takes away those that GitHub denies. A denial takes the user's stored check of that repository away. Faucet keeps a denial only as a marker for 15 minutes, so that an older pass that GitHub gave after the denial cannot come back. An agent must refresh to keep calling once its 15-minute access token expires, so a browser login's `events/poll` and the start of its wait **see a revocation within 15 minutes**, plus the clock skew between faucet's instances, because each instance stamps the checks and the refreshes that it makes with its own clock. A wait that started before then can run for up to 50 more seconds. A refresh never moves a session's refreshed time back, so an instance whose clock lags cannot make older checks count again. `events/subscribe` always asks GitHub.

A GitHub rate-limit answer counts as a failed check that the caller can retry, not as a denial.

**A caller of one target learns nothing from faucet's answers about the events of targets it cannot read.** Every cursor, head, `hasMore`, `maxAgeMs` floor and `truncated` flag, the wait tool's cursor and event `id`, and the `cursor` of a webhook body or a gap envelope is a place among the events of the target that the call or the subscription names (see [cursors](events.md#cursors)). Other targets' events, and purges of them, change none of these values, and a cursor made by hand reads only the named target's events. Two things are not covered: how long an answer takes, because every caller's reads share one database, and [raw events](events.md#raw-events), whose `r1.` cursors still number every repository's raw events together.

**A raw event carries only what every reader of its repository may see.** Faucet checks only that a caller can read a repository, and anyone can read a public one. So faucet drops every `release` delivery of a draft release, which GitHub shows only to people with push access, whatever its action, before it looks for an interest: no lease or subscription gets a draft that arrives after the upgrade (see [raw events](events.md#raw-events)). A draft stored before the upgrade stays until the purge clears raw bodies.

One login can hold 10 waits open at once per process, and run 5 `events/poll` calls at once, typed or raw names together. The call over either limit fails at once, and a poll over it gets `ResourceExhausted` with `data.limit` `polls`. Embedders can change them with `Deps.MaxWaitsPerLogin` and `Deps.MaxPollsPerLogin`. These limits hold per process, so the production deployment also limits each IP address at the edge (see the [firewall](deploy.md#firewall)).

## Principals and scopes

A host that embeds faucet tells it who calls. Its `PrincipalFrom` returns a `Principal` from `NewOAuthUser` (a user of a browser login), `NewService` (a service) or `NewPrincipal` (a GitHub user whose GitHub token `TokenAuthorizer` asks GitHub with, which holds every scope). The wait tool and `events/poll` need `events:read`, `events/subscribe` and `events/unsubscribe` need `events:subscribe`, and `events/list` needs none. A `Principal` built by hand, or one whose `Login` changed after a constructor built it, is no kind of caller: every method but `events/list` answers it `authentication required`.

An `Authorizer` answers `RepoID`, which may remember, and `RepoIDFresh`, which every renewal calls and which must ask again. One that sends each kind of principal to another `Authorizer` passes both calls on. `TokenAuthorizer` answers a caller without a GitHub token with `ErrNoAccess` and asks GitHub nothing. A host that builds a principal from a GitHub token that a caller sent takes on the weakness above: GitHub answers `GET /repos/{owner}/{name}` for a token that cannot read the repository's events. Faucet's browser login builds one only from the token of faucet's own GitHub App.

The `Authorizer` decides a `repo` [target](events.md#targets). An `owner` or `all` target is for a service only: faucet refuses it to every other principal with `ErrNoAccess` and asks nobody. For a service it asks `Deps.ServiceGrants`, which `oauth.ServiceAccess` implements from the client's grants, and without it faucet refuses those targets to a service too. Like an `Authorizer`, it has a fresh form of each call, which every renewal calls and which reads the client again. An `org:` grant covers every repository of the account that held its login when the grant was set, also one made after the grant and under any later login, and `all` every repository that faucet receives deliveries from, private ones included (see [service-accounts.md](service-accounts.md#grants)).

## The browser login

These checks keep another site, another browser and another client from finishing a user's login:

- **Another site cannot press Continue.** The consent page sets a cookie for its own login, and its form carries a token derived from that cookie. Faucet goes on only when the post carries the cookie, the matching form token and an `Origin` that equals `FAUCET_PUBLIC_URL`. Any other post is refused and stores nothing, so a page of another site that posts the form makes nothing. Continue works only once the page has been visible and in focus for 500 milliseconds, so that a page of another site cannot open the consent page under a click that the user meant for that site, such as the second click of a double-click. A press that began before then does not count.
- **Each login has its own cookies.** Their names end with the login's ID, so two logins in one browser do not mix. They are `__Host-` cookies, which only faucet's own origin can set, over `https`.
- **GitHub's answer counts only in the browser that pressed Continue.** The state that faucet sends to GitHub, and the PKCE verifier of faucet's own exchange with GitHub, both derive from a random value in a second cookie. A callback in another browser is refused.
- **Faucet redirects to a client only at the end.** `/oauth/authorize` answers every error with a page and never with a redirect, because nothing proves yet that the browser is the user's. Only the callback redirects to a client, and the redirect names faucet in `iss` (RFC 9207).
- **A code works once, for 60 seconds.** A code that comes back after its redemption ends the session that it made.
- **PKCE runs both ways.** A client must send an S256 challenge and redeem its code with the verifier. Faucet uses PKCE with GitHub too.
- **Refresh tokens rotate.** Each refresh gives a new refresh token. A refresh token that comes back 30 seconds or more after its first use ends its session, because the token then has two holders. Within those 30 seconds it trades again, because the parallel requests of one agent send one token at once. Of the tokens that such requests get, the next refresh retires the ones that the agent did not keep, and one of those that comes ends the session too. Faucet keeps the hash of every refresh token of a session until the session goes, so a stolen token ends the session however late its holder sends it.
- **Client documents come through the guarded client** of [callback URLs](#callback-urls): `https` and public addresses only, and no redirects. Faucet builds that client itself, so a host that embeds faucet cannot give it another. A fetch must end within 3 seconds, and the document must be 5 KiB at most. A document that holds a client secret is refused, because anyone can read it.
- **The consent page shows the host, not the name.** The host of the client ID is the large text, and the name that the document gives is marked as unchecked, because anyone can write any name in a document. The host must be ASCII, with an internationalized name in its `xn--` form, and the name may hold no control or format character, so that neither can pass for another.
- **Redirect URIs match exactly.** A request's redirect URI must equal one of the document's byte for byte, and a loopback `http` one may differ in its port only (RFC 8252). The token request must name the same redirect URI. Schemes that a browser runs, such as `javascript`, are refused.
- **The pages load nothing and run one script,** the wait of Continue, which their Content-Security-Policy allows by its hash. No other site can frame them.

Anyone who serves a valid document can open `/oauth/authorize`, so faucet bounds what that costs. It keeps up to 64 documents, each for as long as its cache headers let a shared cache keep it and 5 minutes at most, and fetches no client ID on its own host. The consent page stores nothing: its form carries the request, sealed with AES-256-GCM for the cookie of the browser that got the page, under a key that HKDF-SHA256 derives from `FAUCET_TOKEN_KEY` for consent forms alone, and faucet stores the request only when that browser presses Continue. So no number of requests uses up anything that another user's login needs. A script can still store rows, one for each GET and POST pair, because it can keep the cookie and send faucet's `Origin` itself. Put a per-IP rate limit on `POST /oauth/authorize` at the edge, such as the Vercel Firewall rule in [deploy.md](deploy.md#firewall); `/cron/purge` deletes such a row once it expires, 10 minutes after the GET. Faucet keeps the failure of a fetch for 1 minute, so a client ID whose fetch failed costs one fetch a minute however often it comes, and logins that start at once share one fetch. A client ID with a new path, or a document sent with `no-store`, still costs one fetch per request. Faucet sets no limit per host, because bad client IDs on a host could use it up and lock out that host's real client.

## Workload identities

A workload logs in as a service client with a token that its platform signed, so faucet trusts the platform's issuer to say which workload holds the token. A trust rule names that issuer and pins claims that only the one workload's tokens hold. Faucet takes a token whose signature verifies with the issuer's key, whose `aud` is faucet's public URL alone, so that a token that the platform made for another service does not log in, and that has not expired. It then mints its own token, which lasts 15 minutes and never past the platform's token. Faucet remembers no platform token, so a copy of one logs in as the client, again and again, until its `exp`. Faucet takes no token that lives more than 24 hours, from its `iat` or `nbf` to its `exp`. Vercel documents 2 hours for the token of a production function. A mounted Kubernetes token lasts its `expirationSeconds`, and one that `kubectl create token` made lasts its `--duration`. Faucet asks the cluster nothing (no TokenReview), so such a token logs in after its pod or its service account is gone, until it expires or the operator runs `faucet clients untrust` or `disable`.

- **An issuer that serves many tenants is pinned to one tenant by ID.** Vercel signs the tokens of every team with the same keys. Faucet requires a Vercel rule to pin the team's and the project's IDs, never only a name that a team can rename and another can take, and it never trusts `https://oidc.vercel.com`, the issuer that every Vercel team shares (see the [Vercel warning](service-accounts.md#example-a-vercel-function)). It refuses the issuers of GitHub Actions, on github.com and on GHE.com (`token.actions.<subdomain>.ghe.com`), and gitlab.com until a test logs in with their tokens. GitHub Enterprise Server and self-managed GitLab fall under the rule for any other issuer, which requires only `sub`, and are not a supported target. A rule for any other issuer must pin `sub`.
- **A platform's token logs in only through the token exchange** (RFC 8693), never as a client assertion (RFC 7523): no grant of faucet's takes one. The platform's token proves which workload calls, and the operator's trust rule, not the token, says which client it may act as.
- **Keys come through the guarded client** of [callback URLs](#callback-urls), which faucet builds itself: `https` and public addresses only, and no redirects. The discovery document and the key set that it names must arrive within 5 seconds together, and each must be 32 KiB at most. Faucet fetches only the issuers that an operator trusted, for a token that names one, so a request cannot make faucet fetch from anywhere else. Pasted keys are never fetched.
- **Faucet keeps an issuer's keys for 5 minutes**, so a key that the issuer drops stops working within 5 minutes. It fetches sooner only for a token whose `kid` the keys lack, and at most once a minute per issuer, so tokens with made-up `kid`s cost one fetch a minute. Within that minute such a token gets the 400 `invalid_client` of a token that no rule verifies, so that a made-up `kid` tells a caller nothing about the client. A key that the issuer adds works from the next fetch. It keeps the keys of up to 64 issuers.
- **A failed fetch keeps the keys that faucet holds** until their 5 minutes end. Faucet keeps the failure for a minute, so while an issuer fails after its keys ran out, faucet answers each login of that issuer 503 `temporarily_unavailable` with `Retry-After` set to the seconds left of the minute, and fetches again at the first login a minute after the failure. The answer names no cause, and the log has it. It does tell a caller with any token that names the issuer that the client trusts the issuer and that its keys fail.

## Callback URLs

In webhook mode faucet makes outbound requests to URLs that clients choose, so it guards them against SSRF:

- **`allowlist` mode** (the default) only sends to origins that the operator listed.
- **Every outbound request**, including handshakes, goes through a guarded client (`faucet.NewHTTPClient`). It speaks `https` only and resolves the host. It refuses the request if any resolved address is not public (loopback, private, link-local, CGNAT, multicast, NAT64 and similar ranges), then dials the address it checked, so DNS can't change between the check and the connection. It follows no redirects, ignores proxy variables, and times out after 5 seconds. It refuses a response that declares a body over 64 KiB or that has headers over 16 KiB, and a delivery attempt that gets one counts as `http_5xx` and is retried. A delivery closes the body unread. A handshake reads its answer, and fails one that is longer than a challenge answer needs.
- A host that resolves to an internal address fails as `connection_refused`, the same as a closed port, so a caller can't map your network.

In `handshake` mode, any public endpoint that answers the challenge can receive events. Use `allowlist` when a public endpoint could front an internal service.

A binary built with `-tags faucet_e2e` lets the guarded client reach loopback over `http`, for the end-to-end tests. No environment variable does this, and the tagged binary logs a warning at start. **Never ship it.**

## Secrets

- **Subscriber secrets** are sealed with AES-256-GCM under `FAUCET_WEBHOOK_KEY`, and never returned or logged.
- **The GitHub tokens of browser logins** are sealed with AES-256-GCM under `FAUCET_TOKEN_KEY`, and never returned or logged. Once no session and no login request names a user's pair, `/cron/purge` deletes it a day after its last update. A sealed token names its user and its field in the data that the seal covers, so a token copied to another row or field does not open. Faucet sends the access token only to `FAUCET_GITHUB_API_URL`, and the refresh token only to GitHub's token endpoint at `FAUCET_GITHUB_URL`, and follows no redirect. A token that does not open fails its user's checks and ends no session (see [rotating the key](browser-login.md#rotate-the-token-key)).
- **`FAUCET_GITHUB_APP_CLIENT_SECRET`** goes only to GitHub's token endpoint, with a user's code or refresh token. Keep it in production only.
- **`CRON_SECRET`** guards the `/cron/*` routes. With it unset, they answer 503 and run nothing.
- **Client secrets** of service clients are shown once, when an operator makes the client, and kept only as SHA-256 hashes.
- **Faucet's own tokens** are kept only as SHA-256 hashes too: access tokens, refresh tokens, codes, and the cookie values and GitHub state of a login in progress. `/cron/purge` deletes each access token once it expires, and each session with its refresh tokens once the session ended or went unused for 180 days. A client revokes a token of its own at `POST /oauth/revoke` (RFC 7009): a refresh token ends its session.
- **`FAUCET_HOOK_TOKEN`** is the only GitHub token that faucet holds for itself. GitHub offers no grant narrower than one that can also edit or delete the hook, so give it to a machine user and keep it in production only. Faucet uses it for exactly two endpoints: listing a hook's deliveries and asking for a redelivery.
- Startup errors name a bad variable but never its value.
